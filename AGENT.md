> Приоритет документов: SPEC.md → DEVELOPMENT_RULES.md → AGENT.md → ADR (§0 правил).

## Обязательное чтение перед работой

1. **[SPEC.md](./SPEC.md)** — что строим, бизнес-инварианты, порядок реализации
2. **[DEVELOPMENT_RULES.md](./DEVELOPMENT_RULES.md)** — правила разработки, чек-листы, запреты
3. **[docs/TASKS.md](./docs/TASKS.md)** — текущие задачи и статусы
4. **[docs/adr/](./docs/adr/)** — зафиксированные архитектурные решения

## Для Разработчика (Claude Code)

### Перед написанием кода
1. Прочитай задачу, SPEC.md и релевантные ADR
2. Напиши **План разработчика** (§6.1 правил): файлы, шаги, тесты, влияние, риски
3. **Жди одобрения плана** — код до одобрения запрещён (§3.3)

### При реализации
- Работай строго в **feature-ветке**, не в `main`
- Пиши тесты до/вместе с кодом
- Запускай `ruff check src/ tests/` + `mypy src/` + `pytest` перед PR
- Нет drive-by изменений (§4.3)
- Нет костылей из §4.2
- Conventional Commits: `feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`

### PR
- Используй шаблон `.github/pull_request_template.md`
- Заполни все пункты чек-листа
- Целевой размер ≤400 строк, максимум ≤800

## Для Проверяющего (Codex)

### Что получаешь
- Дифф PR
- Критерии приёмки задачи
- Результаты тестов
- **НЕ получаешь** рассуждения разработчика (INV-3 в SPEC.md)

### Как проверяешь
1. Полностью пройди чек-лист §6.3 правил (A–F)
2. Проверь каждый пункт §4.2 (признаки костыля) адверсариально
3. Ищи **самый дешёвый способ** пройти тесты, не решив задачу
4. Проверь: не удалены/ослаблены ли существующие тесты

### Вердикт
- **approve** — только если все пункты пройдены
- **request-changes** — с указанием конкретного параграфа правил
- **reject** — при грубом нарушении

**Код не пишешь. Merge не делаешь. Это делает Архитектор после approve.**
