# DEVELOPMENT_RULES.md — Правила разработки

> Нормативный документ. Приоритет: SPEC.md → DEVELOPMENT_RULES.md → AGENT.md → ADR (§0).

---

## §0. Иерархия документов проекта

Приоритет при расхождениях:
1. **SPEC.md** — ЧТО строим (требования, модель данных, инварианты, контракты)
2. **DEVELOPMENT_RULES.md** — КАК работаем (этот файл)
3. **AGENT.md** — инструкции агентам
4. **ADR** — зафиксированные архитектурные решения

Агенты читают SPEC.md и правила перед работой.

---

## §1. Процесс

### §1.1. Двухагентный процесс — обязателен

Любая задача, меняющая защищённую ветку, проходит через двух независимых агентов:
- **Разработчик** (Claude Code) — пишет код и тесты
- **Проверяющий** (Codex) — проверяет по чек-листу §6.3

Запрещено:
- Разработчик коммитит мимо проверяющего
- Проверяющий пишет код
- Один контекст исполняет обе роли

Архитектор может выполнить любую роль вручную при эскалации.

### §1.3. Запрет менять закоммиченный код без согласия

- Нет drive-by правок чужого кода
- Нет переименований/переформатирования «по дороге»
- Нет изменения/удаления чужих тестов
- Нет изменения публичных API, если задача не требует
- Нет rebase/amend/force-push на защищённых ветках

Изменение чужого кода допустимо только если одобрено в плане. Баги — отдельным PR с меткой `fix:`.

### §1.5. Бизнес-инварианты — священны

Ключевые инварианты (в SPEC.md) имеют приоритет процессных правил:
- Каждый инвариант обязан иметь автоматическую проверку, падающую при нарушении
- Изменение инварианта — только двухфазным коммитом с регрессионными тестами
- Производные данные не хранятся отдельно от первичных при риске рассинхронизации

## §2. Роли

### §2.1. Разработчик

- Читает задачу, SPEC, ADR
- Пишет План разработчика до кода (§6.1)
- Получает одобрение плана
- Реализует по плану в feature-ветке
- Пишет тесты до/вместе с кодом
- Гоняет lint/types/тесты
- Создаёт PR
- **Нет прав на merge, force-push, drive-by**

### §2.2. Проверяющий

- Читает задачу, план, PR
- Проходит чек-лист §6.3 **полностью**
- Решает: approve / request-changes / reject
- Делает merge после финального approve
- **Код не пишет**

### §2.3. Архитектор (человек-владелец)

- Решающий голос в спорах
- Право выполнить любую роль вручную
- Утверждение исключений (костыли, обход CI)
- Утверждение крупных архитектурных решений

---

## §3. Коммит-процесс

### §3.2. Однофазный коммит (тривиальные задачи)

Опечатки, правки `*.md` без смысла, патч-бамп зависимостей без breaking changes, косметика CSS без layout. Одно ревью → merge, план не нужен.

Решение о тривиальности — за проверяющим; сомнение → двухфазный.

### §3.3. Двухфазный коммит (стандарт)

- **Фаза 1:** План, проверяющий одобряет (без одобрения код не пишем)
- **Фаза 2:** Реализация и финальное ревью по чек-листу

**Обязателен** для:
- Изменений бизнес-инвариантов
- Изменений SPEC.md
- Миграций БД/схем
- Изменений ≥3 файлов или ≥200 строк

### §3.4. Эскалация и конфликты

1. Обсуждение в комментариях PR со ссылками на SPEC/правила/ADR
2. Если не сошлись за 2 раунда — эскалация Архитектору
3. Решение фиксируется в PR
4. Расхождение с правилами — повод обновить правила отдельным PR

## §4. Качество

### §4.2. Признаки костыля (аудитор указывает конкретный пункт)

1. **Hardcode конфигурируемого** — магические числа, URL, пути, креды в коде
2. **Закомментированный код** — запрещён, кроме TODO с тикетом и сроком
3. **Отключённые тесты** — `.skip`, `.only`, `@pytest.mark.skip` — только с тикетом и сроком
4. **Try/except, глотающий ошибки** — без логирования; `except: pass` — кардинальный костыль
5. **Дублирование** — правило трёх жёсткое
6. **Обход типов** — `Any`, `# type: ignore`, `as unknown as X` без обоснования
7. **Зависимость от внутренних деталей** — приватные пути, `_private`, monkey-patching
8. **Сторонние эффекты в чистых функциях** — глобальный state, ФС/БД из чистой функции
9. **Отключение CI-проверок** — `[skip ci]`, смягчение workflows — только отдельным PR с обоснованием
10. **Длинный TODO без срока** — каждый TODO/FIXME/HACK с тикетом и ответственным
11. **Сильная связанность через глобальное состояние** — singleton-ы, глобальные — только с ADR
12. **Магические строки** — литералы для ветвления → enum/const

Дешёвый способ пройти тесты, не решив задачу → approve невозможен.

### §4.3. Запрет drive-by изменений

Изменения за пределами задачи запрещены. Переименования, переформатирования, «улучшения» соседнего кода — отдельным PR.

### §4.4. Тесты, линт, типизация — обязательны

До merge:
- Все unit- и integration-тесты зелёные в CI
- Линтер без ошибок
- Type-check без ошибок
- **Покрытие нового кода ≥80%** (бизнес-логика) / **≥60%** (UI)
- Новые публичные функции: happy path + edge case + error case
- Каждый бизнес-инвариант покрыт тестом

---

## §5. Защита

### §5.4. Защита веток

Защищённые ветки (`main`, `develop`) технически блокируют нарушения:
- Запрет прямого push (только PR)
- Обязательное прохождение CI до merge
- Обязательный approval (≥1 от проверяющего)
- Запрет force-push
- Запрет удаления ветки
- Linear history при squash-merge

---

## §6. Шаблоны

### §6.1. План разработчика (до кода)

Содержит:
- Ссылку на задачу
- Цель (одно предложение)
- Затрагиваемые файлы (что меняется)
- Шаги
- Тесты (что покрываем, какие edge cases)
- Влияние на другие модули
- Риски
- Открытые вопросы

### §6.2. Шаблон PR

См. `.github/pull_request_template.md`

### §6.3. Чек-лист проверяющего

**A. Соответствие задаче:** реализовано то, что в плане; все шаги; нет лишнего.
**B. Бизнес-инварианты:** не затронуты либо согласованы и покрыты тестами.
**C. Качество кода:** нет паттернов §4.2; осмысленные имена; нет дублирования; нет drive-by.
**D. Тесты:** CI зелёный; покрытие в норме; happy + edge + error; нет отключённых без обоснования.
**E. Документация:** docstring; README модуля; SPEC.md при изменении контрактов; ADR для архитектурных решений.
**F. Git-гигиена:** Conventional Commits; атомарные коммиты; размер PR в норме; нет force-push.

Итог: **approve** / **request-changes** / **reject** + комментарий.

## §7. Фазы проекта

- **Прототип:** инварианты и SPEC обязательны; двухагентность не применяется; тесты желательны
- **MVP:** весь контур §1–§6 в полном объёме; защищённые ветки; первый ADR
- **Production:** + GPG-подписи; E2E на критические сценарии; релизы тегами `vX.Y.Z`
