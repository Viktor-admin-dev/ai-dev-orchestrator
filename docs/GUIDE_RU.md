# AI Dev Orchestrator — Руководство пользователя

## Что это такое

AI Dev Orchestrator — система, которая управляет двумя AI-агентами (разработчик + аудитор) для автоматизации цикла разработки. Вы описываете задачи, оркестратор поручает их AI-разработчику, затем независимый AI-аудитор проверяет результат. Вы как архитектор одобряете план и принимаете финальный результат.

**Роли:**
- **Архитектор (вы)** — ставит задачи, одобряет планы, принимает результат
- **AI-разработчик** (Claude Sonnet/Opus) — пишет код, тесты, исправляет замечания
- **AI-аудитор** (Google Gemini через OpenRouter) — проверяет код, не видя рассуждений разработчика

## Быстрый старт

### 1. Установка

```bash
cd /путь/к/ai-dev-orchestrator
pip install -e ".[dev]"
```

### 2. Инициализация базы данных

```bash
orchestrator init
# Создаёт .orchestrator/state.db
```

### 3. Настройка проекта

Создайте `orchestrator.yaml` в корне целевого проекта:

```yaml
target_project:
  repo: "."                    # путь к репозиторию
  main_branch: "main"         # защищённая ветка
  phase: "prototype"          # prototype | mvp | production

  commands:
    install: "pip install -e ."
    test: "pytest --cov"
    lint: "ruff check src/"
    types: "mypy src/"
    mutation: "mutmut run"     # только для критичных модулей

  critical_modules:            # модули, требующие мутационного тестирования
    - "src/auth"
    - "src/payments"

  budgets:
    per_task_usd: 5.0          # бюджет на задачу ($)
    per_project_usd: 100.0     # общий бюджет ($)

  models:
    developer: "claude-sonnet-4-6"
    developer_critical: "claude-opus-4-8"      # для критичного кода
    auditor: "google/gemini-3.1-pro-preview"   # другой вендор!
    auditor_gateway: "openrouter"
```

> **Важно:** Разработчик и аудитор **обязаны** быть от разных вендоров (INV: vendor independence). Система предупредит при нарушении.

### 4. Создание задач

```bash
# Простая задача
orchestrator add-task T-001 \
  --plan "Реализовать JWT-авторизацию" \
  --criteria "Выдача access/refresh токенов, валидация, middleware" \
  --budget 5.0

# Задача с зависимостями
orchestrator add-task T-002 \
  --plan "API эндпоинты для пользователей" \
  --criteria "CRUD, пагинация, фильтрация" \
  --depends-on T-001 \
  --budget 5.0

# Критичный модуль (потребует мутационное тестирование)
orchestrator add-task T-003 \
  --plan "Модуль обработки платежей" \
  --criteria "Stripe интеграция, идемпотентность" \
  --critical \
  --budget 8.0
```

### 5. Создание стадий

```bash
orchestrator add-stage S1 "Авторизация и API" \
  --task T-001 --task T-002 \
  --budget 15.0

orchestrator add-stage S2 "Платежи" \
  --task T-003 \
  --budget 10.0
```

### 6. Запуск

```bash
# С ручным одобрением планов (рекомендуется)
orchestrator run

# Автоматический режим (всё одобряется без вашего участия)
orchestrator run --auto-approve
```

### 7. Наблюдение через веб-дашборд

```bash
orchestrator serve              # http://127.0.0.1:8080
orchestrator serve --port 9000  # другой порт
```

## Жизненный цикл задачи (12 состояний)

```
DRAFT ──────── Задача создана, ждёт план
  │
  ▼
PLAN_REVIEW ── AI написал план, ждёт вашего одобрения
  │   │
  │   └──── (reject) → DRAFT (переписать план)
  ▼
PLAN_APPROVED ─ Вы одобрили, AI начинает кодить
  │
  ▼
IN_PROGRESS ── AI-разработчик пишет код
  │
  ▼
TESTING ────── Запущены тесты
  │   │
  │   └──── (тесты красные) → REWORK → IN_PROGRESS (повтор)
  ▼
AWAIT_AUDIT ── Тесты зелёные, AI-аудитор проверяет
  │   │   │
  │   │   └── (request-changes) → REWORK → IN_PROGRESS
  │   │
  │   └────── (критичный модуль + approve) → MUTATION
  │                                            │
  │                            (score < 80%) → REWORK
  │                            (score ≥ 80%) ──┐
  ▼                                            ▼
PR_READY ───── Код готов к мержу
  │
  ▼
MERGED ─────── PR смержен
  │
  ▼
ACCEPTED ───── Вы приняли результат ✓

Из любого состояния → FAILED (терминальное, до 3 попыток)
```

### Где требуется ваше участие

| Состояние | Ваше действие | Команда |
|-----------|---------------|---------|
| `PLAN_REVIEW` | Одобрить или отклонить план | `orchestrator approve-plan T-001` или `reject-plan` |
| `MERGED` | Принять результат задачи | `orchestrator accept-task T-001` |
| `REVIEW` (стадия) | Принять стадию после E2E тестов | `orchestrator accept-stage S1` |

В режиме `--auto-approve` всё одобряется автоматически.

---

## Жизненный цикл стадии (6 состояний)

```
PLANNING ────── Стадия создана
  │
  ▼
IN_PROGRESS ─── Задачи выполняются
  │
  ▼ (все задачи завершены)
INTEGRATING ─── Запущены E2E-тесты
  │   │
  │   └──── (тесты красные) → IN_PROGRESS (откат)
  ▼
REVIEW ──────── E2E зелёные, ждёт вашего принятия
  │
  ▼
ACCEPTED ────── Стадия завершена ✓
```

## Команды CLI — полный справочник

### Инициализация и управление

```bash
orchestrator init
```
Создаёт базу данных `.orchestrator/state.db`. Вызывается один раз.

---

```bash
orchestrator add-task <task_id> [опции]
```
Добавляет задачу в состоянии DRAFT.

| Опция | Тип | По умолчанию | Описание |
|-------|-----|-------------|----------|
| `--plan` | TEXT | `""` | Описание задачи / план |
| `--criteria` | TEXT | `""` | Критерии приёмки |
| `--stage` | TEXT | `""` | ID стадии (привязать к стадии) |
| `--budget` | FLOAT | `5.0` | Бюджет в долларах |
| `--critical` | FLAG | `False` | Критичный модуль (мутационное тестирование) |
| `--depends-on` | TEXT | `[]` | ID зависимостей (можно указать несколько раз) |

**Пример:**
```bash
orchestrator add-task T-005 \
  --plan "Кэширование запросов в Redis" \
  --criteria "TTL, инвалидация, fallback при недоступности Redis" \
  --stage S2 \
  --depends-on T-003 --depends-on T-004 \
  --budget 6.0
```

---

```bash
orchestrator add-stage <stage_id> <name> [опции]
```
Добавляет стадию в состоянии PLANNING.

| Опция | Тип | По умолчанию | Описание |
|-------|-----|-------------|----------|
| `--task` | TEXT | `[]` | ID задач (можно несколько раз) |
| `--budget` | FLOAT | `100.0` | Бюджет стадии |

**Пример:**
```bash
orchestrator add-stage S3 "Кэширование и оптимизация" \
  --task T-005 --task T-006 \
  --budget 20.0
```

### Запуск цикла

```bash
orchestrator run [--auto-approve]
```
Запускает основной цикл. Оркестратор будет:
1. Переводить стадии из PLANNING в IN_PROGRESS
2. Для каждой готовой задачи — запускать AI-разработчика
3. Прогонять тесты
4. Запускать AI-аудитора
5. При необходимости — мутационное тестирование
6. Останавливаться на контрольных точках (если не `--auto-approve`)

**Результат:** информация о прогрессе и список ожидающих действий.

---

### Ручные действия (контрольные точки)

```bash
orchestrator approve-plan <task_id>   # одобрить план
orchestrator reject-plan <task_id>    # отклонить план (задача → DRAFT)
orchestrator accept-task <task_id>    # принять задачу (MERGED → ACCEPTED)
orchestrator accept-stage <stage_id>  # принять стадию (REVIEW → ACCEPTED)
```

---

### Наблюдение (CLI)

```bash
orchestrator project     # обзор проекта: стадии, счётчики задач, бюджет
orchestrator stage S1    # детали стадии: задачи, состояние, E2E
orchestrator task T-001  # детали задачи: план, тесты, аудит, стоимость
orchestrator cost        # отчёт по расходам: по модели, задаче, стадии
orchestrator actions     # список ожидающих действий

orchestrator demo        # полная демонстрация с тестовыми данными
```

## Веб-дашборд — страницы

### Dashboard (`/`)

Главная страница — обзор проекта:
- **Метрики:** общее количество задач, в работе, завершённые, упавшие
- **Бюджет:** прогресс-бар расхода (зелёный → жёлтый → красный)
- **Таблица стадий:** ID, имя, состояние, прогресс задач
- Автообновление каждые 3 секунды

### Stage (`/stage/{id}`)

Детали стадии:
- Состояние, бюджет, E2E-тесты
- Таблица задач со ссылками
- История переходов

### Task (`/task/{id}`)

Детали задачи:
- Состояние, попытка, бюджет, критичность
- План и критерии приёмки
- Результаты тестов, вердикт аудитора, мутационное тестирование
- Таймлайн переходов состояний
- Лог разработчика

### Cost (`/cost`)

Отчёт по расходам:
- Общий прогресс-бар бюджета
- Таблица по моделям (стоимость, input/output токены)
- Таблица по задачам
- Таблица по стадиям

### Actions (`/actions`)

Контрольная панель — здесь вы управляете процессом:
- Список ожидающих действий с кнопками **Approve / Reject / Accept**
- Формы для создания новых задач и стадий
- Автообновление каждые 3 секунды

### Log (`/log/{task_id}`)

Полный аудитный лог задачи:
- Хронология всех переходов с таймстемпами и причинами
- Лог разработчика

### JSON API

Для программного доступа:
```
GET /api/project   — статус проекта (JSON)
GET /api/task/{id} — статус задачи (JSON)
GET /api/actions   — ожидающие действия (JSON)
```

## Полный рабочий процесс — пример

### Дано: ТЗ на REST API для блога

**Шаг 1. Инициализация**
```bash
cd ~/my-blog-api
orchestrator init
```

**Шаг 2. Создание `orchestrator.yaml`**
```yaml
target_project:
  repo: "."
  main_branch: "main"
  phase: "prototype"
  commands:
    test: "pytest tests/ --cov=src"
    lint: "ruff check src/"
    types: "mypy src/"
  budgets:
    per_task_usd: 5.0
    per_project_usd: 50.0
  models:
    developer: "claude-sonnet-4-6"
    auditor: "google/gemini-3.1-pro-preview"
    auditor_gateway: "openrouter"
```

**Шаг 3. Декомпозиция ТЗ на задачи**
```bash
# Стадия 1: Фундамент
orchestrator add-task T-001 \
  --plan "Инициализировать FastAPI проект, структура каталогов, базовые модели SQLAlchemy (User, Post, Comment)" \
  --criteria "Приложение запускается, миграция создаёт таблицы" \
  --stage S1 --budget 5

orchestrator add-task T-002 \
  --plan "CRUD для постов: POST/GET/PUT/DELETE /api/posts, пагинация, фильтр по автору" \
  --criteria "Все 4 операции работают, есть тесты, покрытие > 80%" \
  --stage S1 --depends-on T-001 --budget 5

# Стадия 2: Фичи
orchestrator add-task T-003 \
  --plan "JWT-авторизация: регистрация, логин, refresh, middleware" \
  --criteria "Токены выдаются и валидируются, защищённые роуты требуют токен" \
  --stage S2 --depends-on T-001 --budget 5 --critical

orchestrator add-task T-004 \
  --plan "Комментарии к постам: вложенные, мягкое удаление, уведомления" \
  --criteria "CRUD комментариев, вложенность, soft delete" \
  --stage S2 --depends-on T-002 --depends-on T-003 --budget 5

# Стадии
orchestrator add-stage S1 "Фундамент" --task T-001 --task T-002 --budget 12
orchestrator add-stage S2 "Авторизация и фичи" --task T-003 --task T-004 --budget 15
```

**Шаг 4. Запуск оркестратора + веб-дашборд**

Откройте два терминала:

```bash
# Терминал 1 — основной цикл
orchestrator run

# Терминал 2 — веб-дашборд
orchestrator serve
```

Откройте http://127.0.0.1:8080 в браузере.

**Шаг 5. Работа с контрольными точками**

Оркестратор остановится, когда AI-разработчик подготовит план для T-001.

В дашборде на странице `/actions` появится:
- `review_plan` | `T-001` | **[Approve]** **[Reject]**

Нажмите **Approve** чтобы продолжить, или **Reject** чтобы AI переписал план.

После одобрения запустите `orchestrator run` снова — он продолжит с того места.

**Шаг 6. Цикл повторяется**

Для каждой задачи:
1. `run` → AI пишет план → останавливается
2. Вы одобряете план (через веб или CLI)
3. `run` → AI пишет код → тесты → аудит
4. Если аудит прошёл → PR_READY → MERGED
5. Вы принимаете задачу → ACCEPTED
6. Когда все задачи стадии готовы → E2E тесты → вы принимаете стадию

**Шаг 7. Мониторинг стоимости**

Страница `/cost` показывает:
- Сколько потрачено на каждую модель
- Расход по задачам и стадиям
- Прогресс-бар бюджета (при 80% — предупреждение, при 100% — остановка)

## Граф зависимостей

Задачи образуют направленный ациклический граф (DAG). Задача не начнётся, пока все её зависимости не завершены.

```
T-001 ─────┬──→ T-002
           │
           └──→ T-003 ──┬──→ T-004
                         │
              T-002 ─────┘
```

В примере выше:
- T-001 выполняется первой (нет зависимостей)
- T-002 и T-003 могут выполняться параллельно (обе зависят только от T-001)
- T-004 ждёт завершения T-002 и T-003

---

## Бизнес-инварианты (защиты)

Оркестратор жёстко соблюдает 5 правил:

| # | Правило | Как обеспечивается |
|---|---------|-------------------|
| INV-1 | Задача не в PR_READY без зелёных тестов И одобрения аудитора | Guard в FSM |
| INV-2 | Разработчик не коммитит в main | Hook `branch_guard` |
| INV-3 | Аудитор не видит рассуждений разработчика | `EvidencePack.to_auditor_input()` |
| INV-4 | Стадия/задача не ACCEPTED без архитектора | Guard `architect_approved` |
| INV-5 | Бюджет не превышается | `CostTracker` → `BudgetExceededError` |

---

## Повторный запуск (REWORK)

Если тесты красные или аудитор отклонил код — задача переходит в REWORK и AI-разработчик пробует снова. Максимум **3 попытки** (настраивается). После исчерпания попыток задача переходит в FAILED.

---

## Мутационное тестирование

Для задач с флагом `--critical` после одобрения аудитора запускается мутационное тестирование:
- Изменяет код программы (мутанты) и проверяет, ловят ли тесты эти изменения
- Порог: **80%** убитых мутантов
- Если меньше 80% — задача уходит в REWORK для улучшения тестов

## Устранение проблем

### «No database found»
```bash
orchestrator init
```

### Задача застряла в FAILED
Посмотрите историю: `orchestrator log T-001` или `/log/T-001` в дашборде. Причина будет в последнем переходе.

### Бюджет исчерпан
Увеличьте `budgets.per_task_usd` в `orchestrator.yaml` и пересоздайте задачу, либо увеличьте `per_project_usd`.

### Аудитор и разработчик — один вендор
Система выдаст предупреждение при `orchestrator run`. Смените `models.auditor` на модель другого вендора.

### Дашборд не обновляется
Проверьте, что `orchestrator run` запущен в отдельном терминале. Дашборд читает БД каждые 3 секунды — данные появятся, когда `run` сделает переход.
